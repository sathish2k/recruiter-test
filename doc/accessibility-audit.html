Accessibility Audit — AI Recruiter

Static source-code review against WCAG 2.2 Level AA
Stack: Next.js 16 · React 19 · MUI 9 (dark) · react-hook-form + AJV · i18next Scope: packages/shared · packages/modules · recruit-sdk · apps/web (~119 TSX) Date: 15 Jul 2026 Method: manual code review + contrast calc (no live/axe scan)

Executive summary

MUI gives the app good defaults in places — semantic tables, focus-trapped menus/dialogs, lang="en", and landmarks. But the custom design-system layer re-implements several controls as plain <div>/<Box> and detaches labels from inputs. As a result the core flows — logging in, filling forms, navigating pages, filtering tables, and moving pipeline cards — are partially or wholly unusable with a keyboard or a screen reader.

The problems are systemic, not one-off: they live in shared primitives (form-renderer, sidenav, the filter widgets, the theme), so a single fix propagates to every screen — which keeps remediation effort low relative to impact.

Critical

C1Critical

Form inputs have no programmatic label

WCAG 1.3.1 Info & Relationships · 3.3.2 Labels or Instructions · 4.1.2 Name, Role, Value

packages/shared/src/components/form-renderer/form-renderer.tsx — FieldLabel and every TextField

FieldLabel renders a standalone <Typography> with no htmlFor/id link, and the field uses hiddenLabel with no label, aria-label, or aria-labelledby:

export function FieldLabel({ label }) {
  return <Typography>{label}</Typography>;   // detached text, no association
}
<TextField {...field} hiddenLabel placeholder={...} />   // no accessible name

Screen readers announce these as “edit text, blank”. FormRenderer drives sign-in, sign-up, reset-password, add-candidate, add-job and settings — so this hits essentially every form. Highest-impact issue in the audit.

Fix: pass MUI’s label prop (drop hiddenLabel) so a real <label> is associated; or give FieldLabel an id and set aria-labelledby on the input. Apply to the chips input, markdown editor, and segmented control too.

C2Critical

Primary navigation items are non-focusable <div>s

WCAG 2.1.1 Keyboard · 4.1.2 Name, Role, Value · 2.4.4 Link Purpose

packages/modules/recruit-core/src/sidenav/sidenav.component.tsx

<Box onClick={() => router.push(item.routeId)} sx={{ cursor:"pointer" }}>
  <IconRenderer name={item.icon} /> {t(item.label)}
</Box>

Each nav link is a <div> with no tabindex, role, or key handler, so keyboard users can’t focus or activate it and screen readers don’t expose it as a link. Active state is colour/weight only (no aria-current). A keyboard-only user cannot move between pages.

Fix: render each item as <Link component={NextLink} href> (or a Button/MenuItem) and add aria-current="page" to the active item — this also restores a visible focus ring.

C3Critical

Custom radio & checkbox filters are inaccessible

WCAG 1.3.1 · 2.1.1 Keyboard · 4.1.2 Name, Role, Value

filters/components/radio-filter.tsx · checkbox-filter.tsx

Option rows are clickable <Box>s with a purely visual dot/checkmark — no <input>, no role="radio"/"checkbox", no aria-checked, no group semantics, no keyboard handling. AT sees plain text; keyboard users can’t operate them, so table filtering is keyboard-inaccessible.

Fix: use MUI RadioGroup/Radio and FormGroup/Checkbox (correct roles, aria-checked, arrow/space handling), styled to match. If keeping the look, add the roles + aria-checked + tabIndex + onKeyDown manually.

Serious

S1Serious

No semantic headings / document outline

WCAG 1.3.1 · 2.4.6 Headings and Labels

App-wide. renderers/text-renderer.tsx forces component="span"; zero <h1>–<h6> exist. Page titles (appbar, modal) are plain <Typography>. Screen-reader users lose the primary way to scan a page.

Fix: render titles as real headings (Typography component="h1|h2…"); give every route one <h1> (the appbar title is ideal) and nest section headings under it.

S2Serious

Account-menu trigger (avatar) is a clickable <div>

WCAG 2.1.1 Keyboard · 4.1.2 Name, Role, Value

recruit-core/src/appbar/appbar.component.tsx — <Avatar onClick=…>

The avatar opens the profile/logout menu but is non-interactive (only title + cursor:pointer). Keyboard users can’t reach logout; no button role/name.

Fix: wrap it in <IconButton aria-label={t('account')} aria-haspopup="menu" aria-expanded>.

S3Serious

Icon-only buttons without accessible names

WCAG 4.1.2 Name, Role, Value · 2.4.4 Link Purpose

Representative: renderers/actions-renderer.tsx (row actions), modal.tsx (close), toast/toast.tsx (close), form-renderer.tsx (show/hide password), appbar.component.tsx (notifications), plus candidate-detail, hiring, add-job-panel, ai-screening…

Of ~53 IconButtons only a handful have aria-label. MUI icons are aria-hidden, so these announce as just “button”. Some rely on title=, which is unreliable (not shown on keyboard focus/touch).

Fix: add a translated aria-label to every icon-only control; prefer aria-label over title.

S4Serious

Clickable table rows are not keyboard operable

WCAG 2.1.1 Keyboard

table-renderer/table-row.tsx — <TableRow onClick> when rowRouteId is set. Row navigation is mouse-only (no tabindex/role/key handler).

Fix: make the primary cell a real link (best — free keyboard + open-in-new-tab), or add tabIndex={0}, role="link", and an Enter/Space handler to the row.

S5Serious

Kanban drag-and-drop has no keyboard / single-pointer alternative

WCAG 2.1.1 Keyboard · 2.5.7 Dragging Movements (AA, WCAG 2.2)

recruit-pipeline/src/pipeline/pipeline.component.tsx — HTML5 draggable/onDragStart/onDrop. Moving a candidate between stages requires a mouse drag; card open is clickable but move is not.

Fix: add a “Move to…” menu per card (reuse ActionsMenu) and/or adopt a keyboard-capable DnD lib (@dnd-kit keyboard sensor).

S6Serious

Primary button text fails colour contrast

WCAG 1.4.3 Contrast (Minimum)

packages/ui/src/theme.ts — contained/primary gradient #FF8A3C→#E4560F, white 13px text.

Measured: white on #F26A1B = 3.06:1, on #E4560F = 3.73:1, on hover #FF8A3C = 2.35:1. AA needs 4.5:1. The app’s main CTA is below threshold.

Fix: darken the gradient (base ≈ #B23E08) or the text; re-check ≥4.5:1 including hover.

S7Serious

Dialogs/modals are not labelled

WCAG 4.1.2 · 1.3.1

modal/modal.tsx — Dialog has no aria-labelledby/aria-describedby; title has no id; close IconButton has no aria-label.

Fix: give the title an id and pass aria-labelledby (+ aria-describedby) to Dialog; label the close button.

S8Serious

Native date/number inputs remove focus outline & have no label

WCAG 2.4.7 Focus Visible · 1.3.1 · 3.3.2

filters/components/filter-popover.tsx DARK_INPUT_STYLE (outline:"none") used by date/daterange/range filters. Raw <input>s lose the focus ring with no replacement and have no associated <label>.

Fix: remove outline:none (or add a :focus-visible ring) and add aria-label (from/to, min/max) to each input.

Moderate

M1Moderate

Search field labelled only by placeholder

WCAG 1.3.1 · 3.3.2 · 4.1.2 — filters/components/search-filter.tsx

Add inputProps={{ 'aria-label': t('search') }}. Placeholder also disappears on input and is low-contrast (see M4).

M2Moderate

No status-message live regions

WCAG 4.1.3 Status Messages

Zero aria-live/role="status"/role="alert" in the codebase. Toasts (toast/toast.tsx) and async results aren’t announced. Wrap toast content in role="status" aria-live="polite" (assertive for errors).

M3Moderate

Segmented control uses tab semantics for a form value

WCAG 4.1.2 — form-renderer.tsx “segmented” widget

Tabs/Tab (tablist/tab roles) are used to pick a field value; AT hears “tab” for a single-select. Use a RadioGroup or ToggleButtonGroup with a label.

M4Moderate

Secondary / hint / placeholder text fails AA contrast

WCAG 1.4.3 — theme text.disabled #7C7972

Measured 3.93:1 on panel / 4.24:1 on input bg; used for placeholders, hints, sidenav group titles, overline. Below 4.5:1 for small text. Lighten toward #9A968E (which passes at ~5.8:1).

M5Moderate

No “skip to main content” link

WCAG 2.4.1 Bypass Blocks

Keyboard users tab through the full sidenav on every page. Add a visually-hidden-until-focused skip link targeting the <main> in mui-core-layout.tsx.

M6Moderate

Charts likely lack a text alternative

WCAG 1.1.1 Non-text Content

ApexCharts is used in dashboard funnels/KPIs (graph-renderer). SVG charts are typically opaque to AT — provide a caption/summary or an equivalent data table and an aria-label. Verify per chart.

M7Moderate

Multiple unnamed <nav> landmarks

WCAG 1.3.1 / 2.4.1 — sidenav.component.tsx

component="nav" renders once per group, producing several unnamed <nav> landmarks. Use one <nav aria-label={t('primary')}> around all groups.

M8Moderate

IconRenderer image alt defaults to empty

WCAG 1.1.1 — renderers/icon-renderer.tsx

<Box component="img" alt="">: meaningful images passed via src (logos, avatars) default to decorative and are dropped by AT. Propagate a meaningful alt.

M9Moderate

Chips input & delete affordance in forms

WCAG 1.3.1 / 4.1.2 — form-renderer.tsx chips widget

The InputBase has no label association and the per-chip onDelete may lack a name (e.g. “Remove React”). Associate the label and set an aria-label on delete.

Minor / best-practice

L1Minor

Active nav/tab state relies on colour + weight only

WCAG 1.4.1 Use of Colour

Add aria-current to sidenav (covered by C2). MUI Tabs already sets aria-selected.

L2Minor

Notification “unread” indicated by a colour dot only

WCAG 1.4.1 / 1.1.1 — appbar.component.tsx badge dot

Add an aria-label (“unread notifications”) or a visually-hidden count.

L3Minor

No prefers-reduced-motion handling

WCAG 2.3.3 Animation from Interactions (AAA — advisory)

Card hover translateY, transitions, and toast motion ignore reduced-motion. Gate non-essential motion behind @media (prefers-reduced-motion: reduce).

L4Minor

Hard-coded English accessible name

Consistency / localisation — renderers/actions-menu.tsx

aria-label="actions" is untranslated while the app is i18n-driven. Route it through t().

What’s already good

  • lang="en" is set on <html> (apps/web/src/app/layout.tsx).
  • Tables use semantic MUI Table/TableHead/TableCell — header cells render as <th scope="col">, sortable headers use TableSortLabel.
  • <main> and <aside> landmarks exist (core layout + sidenav).
  • MUI Menu/Dialog/Popover provide focus trapping, focus return, and Escape-to-close for free.
  • Form validation errors are wired correctly — TextField helperText + error give aria-describedby and aria-invalid.
  • External links get rel="noopener noreferrer" + target handling.
  • Most body text and all “soft” status chips comfortably pass AA (5.6:1–8.1:1); switch/checkbox widgets use FormControlLabel.

Suggested remediation order

  1. C1 form labels & C2 sidenav links — highest impact, each a single shared-component fix.
  2. C3 filter controls, S2 avatar button, S3 icon-button labels — swap to semantic MUI / add aria-label.
  3. S6 / M4 contrast — a theme-only change (button gradient + text.disabled).
  4. S1 headings, S7 dialog labelling, S4 table rows, S8 focus outline — structural but localized.
  5. S5 kanban, M2 live regions, M3 segmented, M5 skip link, M6 charts — larger / feature-specific.
  6. Minor items + an automated pass (@axe-core/playwright) wired into the existing e2e suite to catch regressions.
This is a static code review — it catches structural and code-level issues but not everything a live assistive-technology test would (focus order, reading order, real screen-reader output). A follow-up axe scan plus a manual keyboard/VoiceOver pass on the running app is recommended before claiming conformance.
